Markdown → HTML はほぼ無損失です。HTML → Markdown はそうではなく、これからも
そうなりません。

理由は構造的です。HTML は Markdown よりはるかに多くを表現できます。入れ子の
`<div>`、インラインの `style`、任意の属性、列をまたぐセル — Markdown には対応する
概念がありません。コンバーターは何を**捨てるか**を決めなければならず、その判断は
すべて匙加減を伴います。

## 誰もが使うライブラリ

標準は `turndown` で、表と取り消し線には `turndown-plugin-gfm` を足します。

```javascript
import TurndownService from 'turndown';
import { gfm } from 'turndown-plugin-gfm';

const td = new TurndownService({
  headingStyle: 'atx',        // 下線ではなく #
  codeBlockStyle: 'fenced',   // インデントではなく ```
  bulletListMarker: '-',      // * ではなく -
});

td.use(gfm);
const markdown = td.turndown(html);
```

この 3 つのオプションは見た目以上に重要です。既定値では `setext` 見出し
（`===` で下線を引く形式）、インデントのコードブロック、`*` の箇条書きが出力されます。
いずれも正規の構文ですが、代替手段より移植性が劣ります。

## きれいに残るもの

| HTML | Markdown | 備考 |
| --- | --- | --- |
| `<h1>`–`<h6>` | `#`–`######` | `atx` スタイル時 |
| `<strong>`, `<b>` | `**太字**` | |
| `<em>`, `<i>` | `*斜体*` | |
| `<a href>` | `[テキスト](url)` | 相対 URL はそのまま |
| `<img>` | `![alt](src)` | `alt` が代替テキストになる |
| `<ul>`, `<ol>` | `-` / `1.` | 入れ子は保持 |
| `<blockquote>` | `>` | |
| `<pre><code>` | フェンスブロック | 言語は `class` から推測 |
| `<table>` | GFM 表 | プラグインと `<th>` が必要 |

## 残らないもの

**見た目に関するもの全般。** `<div>`、`<span>`、インラインの `style`、`class` —
すべて消えます。それが Markdown の目的ですが、独自のレイアウトに依存していた場合は
失われます。

**結合セル。** `colspan` と `rowspan` に対応する Markdown はありません。典型的な結果は、
結合セルの内容が先頭列に入り残りが空になる表です。表全体がプレーンテキストに
崩れることもあります。

**入れ子の表。** Markdown には存在しません。戻ってくると思わないでください。

**段落内の `<br>`。** Markdown の改行は行末スペース 2 つですが、ほとんどのエディターは
保存時に削除します。現実的な解は `<br>` を生の HTML として残すことです。大半の
レンダラーが受け付けます。

**定義リスト `<dl>`。** 対応する構文がなく、段落になるか消えるかします。

**意図していないインライン装飾。** スタイルシートで font-weight が当たった `<span>` は
turndown には見えません。タグは見ますが計算済みスタイルは見ないからです。ページ上で
**太字に見えていた**テキストが、素のまま出力されることがあります。

## 逃げ道：HTML を残す

Markdown に対応するものがない場合、turndown に手を付けさせないよう指示できます。

```javascript
td.keep(['details', 'summary', 'iframe']);
```

指定したタグはそのまま通過します。折りたたみセクションや埋め込み動画を残すには
こうします。ただし出力先のレンダラーが `html: true` であることが前提です。生の HTML を
エスケープするプラットフォームでは、タグが文字列として表示されます。

## 空白の問題

これで半日を失う人がいます。

ブラウザーはインラインタグ間の空白を無意味なものとして扱いますが、Markdown は
そうではありません。たとえば次の HTML は、

```html
<p>Hello <strong>world</strong>, welcome.</p>
```

コンバーターがテキストノードをどう正規化するかによって、
`Hello **world** , welcome.` になることがあります — カンマの前の空白に注意してください。
対策は、変換前にインライン要素の境界周辺の連続した空白を整理することです。良い
コンバーターが生の文字列ではなく DOM を前処理するのはこのためです。

同じ問題は入れ子リスト周辺の不要な空行としても現れます。整形された HTML の
`</li>` と `<ul>` の間の改行がテキストノードになるからです。

## 実際に効く前処理

コンバーターに渡す前に、次の 3 パスで現実の文書の大半は改善します。

1. **除去**：`<script>`、`<style>`、`<noscript>`、コメント、トラッキングピクセル
2. **アンラップ**：意味を持たず子が 1 つだけの `<div>` は、その子で置き換える
3. **正規化**：インライン要素の内側と周辺の空白

これを行うだけで、Markdown 側でどれだけ正規表現を後処理するより出力が良くなります。
壊れた Markdown を後から直すのは、先に HTML をきれいにするよりずっと大変です。
後では、どの改行に意味があったのか分からなくなっているからです。

## 変換をやめるべきとき

手で書かれた文書なら、変換する価値はたいていあります。Web アプリが描画した結果 —
20 重の div、ユーティリティクラス、インラインスタイル — なら、元のソースに戻った
ほうが良いでしょう。コンバーターは文書には最善を、機械生成の DOM には最悪を
発揮します。

[HTML → Markdown](/ja/html-to-markdown/) にマークアップを貼り付け、採用する前に
結果を読んでください。出力の手直しに数分以上かかるなら、そのソースは出発点として
間違っています。
