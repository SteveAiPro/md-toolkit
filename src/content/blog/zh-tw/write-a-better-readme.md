README 只有一個任務：讓一個陌生人從「這是什麼」走到「我會用了」，愈快愈好。多數 README
失敗，是因為它們是為作者寫的，不是為讀者寫的。

好消息是，格式幾乎已經有標準答案了。有一個有效的結構，偏離它很少有好處。

## 結構

由上到下，依序是：

1. **名稱和一句話描述。** 不是標語。它到底做什麼，照實寫。
2. **一張截圖或短 GIF**（如果這東西有視覺產出）
3. **安裝。** 一條可以直接複製貼上的指令。
4. **用法。** 能做出有用結果的最小範例。
5. **設定 / API 參考**（如果有的話）
6. 最底下放**貢獻方式**和**授權**。

就這樣。注意沒在清單上的東西：專案狀態區、理念宣言、路線圖、十二行深的徽章表格。

## 四個錯誤

**1. 沒有安裝指令。** 最常見的失敗。讀者有興趣，往下滑想找怎麼開始，結果看到一整面
散文和一個 wiki 連結，然後離開。把指令放在第一個螢幕畫面內的圍欄區塊裡。

**2. 用法範例寫成整份 API。** README 該展示的是 *hello world*，不是所有選項。其他東西
放文件站或另一個檔案。如果你的用法區段需要目錄，那它對 README 來說太長了。

**3. 拿徽章當內容。** 頂端六個徽章只傳達了「這個專案有人維護」，沒有別的。留下有意義的
兩三個——建置狀態和版本——然後往下走。

**4. 過時的截圖。** 比沒有截圖更糟。圖片拍攝之後 UI 改過了，會讓讀者懷疑整份文件。
如果你沒辦法維持更新，就用程式碼區塊代替。

## 值得做的細節

**讓複製貼上真的能用。** 這裡就是 Markdown 細節發揮的地方。shell 指令放在標了語言的
圍欄區塊裡：

````markdown
```bash
npm install your-package
```
````

不要在行首放 `$` 提示符。它看起來很道地，但會毀掉複製貼上——讀者每次都得手動避開它。

**連到章節，不是連到檔案。** 自動產生的標題 ID 讓你能寫
`參見[設定](#設定)`。錨點記得驗證，slug 規則各家渲染器不同。

**選項用表格。** 二十行的散文式選項清單沒人看得下去。名稱、預設值、說明三欄才是對的
形狀：

```markdown
| 選項 | 預設值 | 說明 |
| --- | --- | --- |
| `timeout` | `5000` | 請求逾時（毫秒） |
| `retries` | `3` | 判定失敗前的重試次數 |
```

**把長尾收起來。** 原生 `<details>` 在 GitHub 上能用：

```markdown
<details>
<summary>完整選項清單</summary>

...很長的內容...

</details>
```

這是 Markdown 裡的原始 HTML。在 GitHub 和現代靜態產生器上可行，在會逸出 HTML 的平臺上
會失效。依賴它之前先搞清楚你的讀者是誰。

**寫清楚它不做什麼。** 一小段「非目標」或「限制」能幫你省下 issue，也幫讀者省下一個
白費的晚上。這招被嚴重低估。

## 長度

沒有正確的長度，但有正確的**形狀**：文件愈往下，內容愈專門。應該要有人在讀完用法區段
就停下來，而且能成功。

如果你的 README 超過大約兩個螢幕，多出來的內容大概屬於 `docs/`。從 README 連過去，
不要內嵌。

## 把 README 拿到別的地方用

README 常常是你手上最好的行銷文案。兩個值得知道的轉換：

**轉成圖片。** 把 README 渲染成截圖——名稱、描述、安裝指令、範例都在一張圖裡——是一則
不錯的社群貼文。超過某個長度圖片就沒法讀了，所以裁到最上面那一段就好。
[Markdown 轉圖片](/zh-tw/markdown-to-image/) 會輸出成 PNG。

**轉成 PDF。** 適合交給活在 Word 裡的人的內部文件，或是跟某個版本一起封存文件。
[Markdown 轉 PDF](/zh-tw/markdown-to-pdf/) 用的是瀏覽器列印引擎，所以程式碼區塊會正確
跨頁斷行，不會被切一半。

## 五分鐘測試

找一個從沒看過這專案的人，請他照著你的 README 做，並告訴你卡在哪裡。他卡住的地方就是
該修的地方——而且幾乎永遠不是你以為不清楚的那個地方。

在 [Markdown 編輯器](/zh-tw/markdown-editor/) 裡打草稿，你才能邊寫邊看到渲染後的結構。
把 README 當原始 Markdown 來讀，正好會蓋掉讀者會踩到的問題。
