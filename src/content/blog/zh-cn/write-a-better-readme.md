README 只有一份工作：让一个陌生人尽快从"这是什么"走到"我会用了"。大多数 README
失败，是因为它们是写给作者自己看的，不是写给读者看的。

好消息是这个格式几乎已经被解决了。存在一个有效的结构，偏离它基本没好处。

## 结构

从上到下，按顺序：

1. **名字 + 一句话描述。** 不是口号，是字面意义上它干什么。
2. **一张截图或一段短 GIF**，如果这个东西有可视化输出。
3. **安装。** 一条能复制粘贴的命令。
4. **用法。** 能做点有用之事的最小示例。
5. **配置 / API 说明**，如果有的话。
6. **贡献方式**和**许可证**，放最底下。

就这些。注意没在列表里的东西：项目状态、理念宣言、路线图、十二行深的徽章墙。

## 四个致命错误

**1. 没有安装命令。** 最常见的一个。读者已经感兴趣了，往下滚找怎么开始，看到一堵
散文墙和一个 wiki 链接，然后走了。把命令放进首屏的栅栏块里。

**2. 把整个 API 当用法示例。** README 该展示的是 *hello world*，不是每一个选项。
其余的放进文档站或单独的文件。如果你的用法章节需要目录，那它对 README 来说太长了。

**3. 用徽章代替内容。** 顶部六个徽章传达的信息只有"这个项目有人维护"，别的什么
都没有。留两三个真有意义的——构建状态和版本号——然后往下走。

**4. 过期的截图。** 比没有截图更糟。界面已经变了而图还是旧的，会让读者怀疑整份文档。
没法保持更新的话，用代码块代替。

## 值得做的细节

**让复制粘贴真的能用。** 这里 Markdown 的细节就重要了。shell 命令放进带语言标注的
栅栏块：

````markdown
```bash
npm install your-package
```
````

不要在行首放 `$` 提示符。它看着挺像那么回事，但会毁掉复制粘贴——读者每次都得手动
避开它。

**链到章节，不要链到文件。** 自动生成的标题 ID 让你可以写
`见 [配置](#配置)`。锚点要验证，slug 规则各渲染器不一样。

**选项用表格。** 二十行的纯文本选项列表没法读。三列——名称、默认值、说明——是合适的
形状：

```markdown
| 选项 | 默认值 | 说明 |
| --- | --- | --- |
| `timeout` | `5000` | 请求超时（毫秒） |
| `retries` | `3` | 失败前的重试次数 |
```

**长尾内容折叠起来。** 原生 `<details>` 在 GitHub 上可用：

```markdown
<details>
<summary>完整选项列表</summary>

……很长的内容……

</details>
```

这是在 Markdown 里写原始 HTML。它在 GitHub 和现代静态生成器上行，在会转义 HTML 的
平台上会失败。依赖之前先搞清楚读者在哪看。

**说清楚它不做什么。** 一小节"非目标"或"已知限制"能省掉一堆 issue，也能省掉读者
一个白费的晚上。这节被严重低估。

## 长度

没有标准长度，但有标准的**形状**：越往下内容越专门。读者应该能在读完用法章节后
停下来并且成功。

如果 README 超过大约两屏，多出来的内容大概属于 `docs/`。从 README 链过去，不要
内联进来。

## 把 README 用到别处

README 往往是你手上最好的营销文案。两种转换值得知道：

**转成图片。** 把 README 渲染成图——名字、描述、安装命令、示例一屏打尽——是一张像样
的社交平台配图。超过一定长度图就没法读了，所以只截顶部那一段。
[Markdown 转图片](/zh-cn/markdown-to-image/) 可以把它渲染成 PNG。

**转成 PDF。** 适合交给活在 Word 里的同事的内部文档，或者随版本归档一份。
[Markdown 转 PDF](/zh-cn/markdown-to-pdf/) 走浏览器打印引擎，代码块能正确分页，
不会从中间被切开。

## 五分钟测试

找一个从没看过这个项目的人，让他照着你的 README 走一遍，告诉你在哪卡住了。他卡住
的地方就是该改的地方——而且它几乎从来不是你以为的那个不清楚的地方。

在 [Markdown 编辑器](/zh-cn/markdown-editor/) 里边写边看渲染结果。把 README 当纯
Markdown 读，恰恰会掩盖读者真正会撞上的问题。
