简短回答：能。长一点的回答：能，但你得先搞清楚 `.docx` 到底是什么，否则结果不会
是你想要的样子。

## 为什么这件事比听起来难

Markdown 是一门轻量标记语言，大概二十个概念。Word 的 `.docx` 是 OOXML 包——字面
意义上就是个 ZIP 文件，里面装着描述样式、编号定义、分节符、嵌入字体和图形锚点的
XML。这两者形状完全不同。

转换器不是在把一种格式翻译成另一种，它是在**凭空补全**大量 Markdown 里根本不存在
的结构：标题用什么字体？段后间距多少？表格的边框从哪来？

这就是为什么粗糙的转换器产出的文档，虽然能在 Word 里打开，但看起来像一个迷路的
纯文本文件。

## 什么能保留

| Markdown | 在 Word 里 | 说明 |
| --- | --- | --- |
| `#`–`######` | 标题 1–6 样式 | 用的是 Word 内置样式，导航窗格能正常工作 |
| `**粗体**` / `*斜体*` | 加粗 / 倾斜 | 行内保留 |
| 列表 | 编号 / 项目符号列表 | 嵌套层级保留 |
| 表格 | 真正的 Word 表格 | 不是用制表符假装成表格 |
| ```` ```代码``` ```` | 等宽字体段落 | 没有语法着色——Word 没有这个概念 |
| 链接 | 超链接域 | 仍然可以点击 |
| 图片 | 嵌入图片 | 见下面的警告 |
| `>` 引用 | 带左边框的缩进段落 | 近似实现 |

## 什么会丢

**语法高亮。** Word 无法在一个段落里表示彩色 token，除非把文本整个扔掉换成图片。
代码块会以等宽字体的形式出现。需要彩色代码的话，导出成 HTML 或 PDF。

**公式。** 除非转换器先把 KaTeX 渲染成图片，否则 `$E = mc^2$` 到达时就是字面的
美元符号。

**自定义 CSS。** Markdown 本身没有样式，但如果你是从 HTML 转过来，所有 `class` 和
内联样式都会被丢掉。长什么样由转换器说了算。

**脚注和任务列表。** 支持程度不一。有些转换器把 `- [ ]` 变成真正的复选框域，
大多数渲染成字面的 `[ ]`。

## 两个会搞坏图片的问题

如果你的 Markdown 引用了图片而转出来是空的，一定是这两个之一。

**1. Word 的图片元素不支持 WebP。** OOXML 的 `ImageRun` 只接受 PNG、JPEG、GIF 和
BMP。丢给它一段 WebP 字节流，Word 就显示一个空框。解决办法是先把图片解码到 canvas，
重新编码成 PNG 再嵌入。

**2. 跨域图片会污染画布。** 用 `fetch()` 取远程图片受 CORS 限制，把它画进 canvas
之后画布就被"污染"了，之后调用 `toBlob()` 会抛安全错误。绕法是改用
`<img crossOrigin="anonymous">` 元素加载再画进 canvas，绕开 fetch 这条路径。
但这只在远程服务器愿意给宽松 CORS 头时才有效。

大多数浏览器端转换器这两条一条都没处理，所以"我的图片不见了"是排名第一的投诉。

## 本地转换 vs 上传到网站

浏览器端转换有个实实在在的隐私理由：每一个接受文件上传的在线转换器，都把你的
文档存在了别人的服务器上，哪怕只是短暂的。如果那是份没公开的合同草稿或者未发布的
公告，这就很要紧。

完全在你自己浏览器里跑的转换器，一个字节都不会发出去。你可以打开 devtools 看
network 面板验证——不应该有任何包含你文本的 POST 请求。

试试 [Markdown 转 Word](/zh-cn/markdown-to-word/)：左边粘贴文本，右边实时预览，
点下载时 `.docx` 在你自己的浏览器里生成。

## 转换前的检查清单

- 图片用绝对 URL 或 data URI，不要用相对路径
- 能避开 WebP 就避开
- 标题用 `#` 语法，不要手动加粗单独一行
- 表格有 `---` 分隔行
- 发给别人之前，自己先打开看一遍
